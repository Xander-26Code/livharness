# LivHarness

[English](README.md) | [简体中文](README_ZH.md)

**一个实验性的 Agent Harness，探索如何让“任务完成”的报告有检查结果和证据支撑。**

LivHarness 是一个 Python 项目，负责把大模型和工具连接起来，管理 Agent 完成任务的过程。

> **初级开发阶段 · v0.2 核心功能已完成，尚未正式发布。** 当前支持流式输出、文件工具、结构化工具结果和对话保存。现在开始 v0.3：记录实际检查了什么、哪些失败、哪些仍不确定。验收机制尚未实现。

## 我们想做出什么

### 1. 让完成声明有据可查 — Verified Agent Execution

Agent 说“完成了”还不够。我们希望 harness 记录任务要求，对实际结果执行检查，并展示每个验收状态背后的证据。

例如，用户要求把端口改为 `8080`，其他配置不变。只检查端口还不够，系统也需要比较其余配置，并报告意外改动。

系统无法自动知道任意任务的正确标准。每项检查都需要明确范围和来源。模型可以建议检查条件，但建议不会自动成为用户要求或成功证明。缺少证据时，结果应该保持未验证。

### 2. 长任务中保持方向 — State-Aware Context Engineering

每次调用模型时，让它知道最新的目标、重要限制、尚未解决的问题，以及文件或环境发生的变化。

例如，用户中途改变要求，Agent 应该按新要求继续；对话变长后，仍然记得“不要修改这个文件夹”；文件被改动后，也知道之前读取的内容可能已经过时。

我们希望根据任务进展选择下一步需要的信息，减少无用历史，同时保留影响后续操作的关键内容。

我们会从本地文件任务开始，验证这些设计能否让任务完成得更好、减少重复操作，并控制成本。

## 现在能做什么

目前的原型支持：

- 与 DeepSeek 对话，让模型调用工具。
- 读取文本、列出目录、查找文件。
- 替换文件中唯一匹配的文本。
- 使用 `pypdf` 提取 PDF 文字，不支持 OCR 或图片理解。
- 保存对话、加载历史会话、查看最近的会话。
- 连续滚动的终端界面，支持流式回答、Markdown 排版、工具状态、可编辑输入和会话命令。
- 查看结构化工具结果，使用 Ctrl+C 停止本轮，达到10轮上限后保留过程记录。

任务结果检查和状态感知上下文管理仍在规划中。工具返回成功，还不等于系统已经独立验证整个任务完成。加载会话恢复的是已保存的消息，不能准确恢复任务中断时的执行状态。

## v0.3：先实现什么

**目标：**对已登记、有依据的要求执行检查，生成不超出证据范围的系统报告。以下是开发计划，尚未实现。

先从本地文件和配置修改开始。第一批实验由用户或任务作者提前指定验收条件，自动发现条件留到后续研究。

| 记录 | 保存什么 |
| --- | --- |
| 任务 | 用户原始请求及后续变更 |
| 验收条件 | 检查什么、依据在哪里、是否已经确认用于本次任务 |
| 检查记录 | 实际执行的检查、观察结果，以及对应的条件版本和相关文件版本 |
| 系统报告 | 哪些检查通过、失败或仍未验证，以及对应证据 |

第一版必须遵守这些规则：

- **要求可追溯。** 保留原始请求和变更记录。模型不能悄悄删除要求，也不能把自己的建议标成用户已确认。来源真实不代表理解正确；歧义未解决前，要明确保留。
- **由 harness 执行检查。** 检查记录来自检查器的实际运行。工具返回成功，或模型自行填写 `passed`，都不能代替验收证据。
- **证据对应当前版本。** 记录检查时的条件与文件版本；任何一方变化，都需要重新检查。文件指纹只能发现变化，不能证明条件正确，也不代表整个环境没有变化。
- **报告与模型回答分开。** 系统报告由程序规则生成，与模型流式回答分别展示。全部已登记检查通过，只能说明这个检查范围通过，不能说明所有可能的要求都已发现或满足。

第一个里程碑是配置修改任务，需要通过四种验收案例：

1. 目标值修改正确，其他配置不变：检查通过。
2. 工具报告成功，但实际文件没有修改：检查失败。
3. 目标值改对了，但其他配置也被误改：保持原配置的检查失败。
4. 检查通过后文件再次变化：旧结果不能继续证明当前文件通过。

尚未执行的检查、无法读取的文件和未明确的条件，都必须保留为未验证，并记录原因。先用普通 Python 模块和确定性的文件检查完成流程，这个里程碑不要求多个验证 Agent。

## 验证流程之后的研究方向

我们希望研究：如何从任务上下文、测试和文档中发现有用的候选条件，主动寻找反例，并在预算内选择值得执行的检查。这些是尚无确定版本号、尚未证明收益的实验方向，将建立在上述验收记录和 v0.4 上下文管理的基础上。

相关研究包括 [VeriHarness](https://arxiv.org/abs/2610.00972)、[LLM 生成测试判定规则](https://arxiv.org/abs/2607.10277)和 [LEDGER](https://arxiv.org/abs/2608.18398)。我们提出的组合是研究方向，尚不能宣称具有已经证实的原创性或性能优势。

我们计划在相同任务、模型和相近预算下，对比普通 Agent 循环、固定检查，以及后续的动态检查。评测使用独立准备、对 Agent 隐藏的参考标准，同时记录任务实际成功率、错误完成声明、漏报有效完成、无法判断的情况，以及耗时和 token 成本。不能让“永远回答不知道”获得成功评价。目前还没有评测结果。

## 快速开始

需要 Git、Python 3.10+，以及能够访问当前配置模型的 DeepSeek API Key。

```bash
git clone https://github.com/Xander-26Code/livharness.git
cd livharness
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

如果你的 Python 3.10+ 解释器使用其他命令，请替换上面的 `python`。Windows PowerShell 使用 `.venv\Scripts\Activate.ps1` 激活环境。

### 配置

在项目根目录创建 `.env` 文件：

```dotenv
DEEPSEEK_API_KEY=replace_with_your_own_key
```

当前模型配置为 `deepseek-flash`。模型名称和 API 地址可在 [agent_loop.py](agent_loop.py) 中修改。不要提交自己的密钥；Git 已忽略 `.env`。

在仓库根目录启动：

```bash
python main.py
```

可以试着输入：`请读取 tools/read_file.py，解释它做了什么。`

**请先使用测试文件或副本。** 当前程序直接修改文件，没有沙箱或自动回滚。文件内容可能发送给模型服务，模型调用会使用你的 API 账户。

## 使用方式

| 命令或输入 | 作用 |
| --- | --- |
| `python main.py` | 启动终端界面，开始新对话 |
| `python main.py --demo` | 离线预览，不调用 API、不写入会话 |
| `python main.py --plain` | 使用无颜色、无动画的基础输入模式 |
| `python main.py --list-sessions` | 查看已保存的会话，最近更新的在前 |
| `python main.py --resume SESSION_ID` | 加载历史对话；将 `SESSION_ID` 替换为实际会话 ID |
| `/help` | 查看命令与快捷键 |
| `/new` | 新建会话，保留原会话 |
| `/sessions` 或 `/resume` | 查看带标题和编号的会话列表 |
| `/resume 编号` 或 `/resume ID` | 按最近展示的列表选择，或使用完整会话 ID |
| `/session` | 查看当前完整会话 ID |
| `/details` | 开关后续工具结果的完整 JSON 展示 |
| `/clear` | 清空当前对话，已经修改的文件不会恢复 |
| `/exit`、`exit` 或 `quit` | 保存并退出 |

界面提示统一使用英文，对话内容保留原本语言。在 `❯` 后输入命令。Enter 发送，Ctrl+J（或先 Esc 再 Enter）换行，方向键浏览输入历史，Tab 补全命令。Ctrl+C 清空输入或停止正在运行的这一轮。停止不会撤销文件修改；没有记录结果的工具需要先核实状态再重试。

收到回答文字后会逐段显示，`--plain` 模式也支持。当前开启了思考模式，因此回答开始前可能需要等待，界面不展示思考正文。普通 TUI 中，较长的回答在生成时预览末尾内容，结束后将完整 Markdown 回答保留在终端滚动历史中。生成中断时，已显示的文字会标记为未完成，不会作为完整的助手回答保存。

只有调用模型时才需要 API key。帮助、预览和会话命令可离线使用。界面代码放在 [tui/](tui/)，通过 Agent 回调接收回答与执行进度。
